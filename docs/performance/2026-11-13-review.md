| P2 | `helmet_realtime.py:410` 的自动保存分支只有 `pass` | CLI 提供了尚未实现的功能；应实现并验证，或明确拒绝该参数 |
| P2 | `QoS` 仅保留最近 30 次检测，最终却打印 Session Avg | 输出是滑动窗口统计，不能代表整段实验；需要分开窗口与会话累计统计 |
| P2 | `deploy.cmd` 未检查各次 SSH/SCP 返回码；检查只导入 `yolo_post` | 上传失败或实时脚本语法错误也可能出现部署完成提示 |

`benchmark.py` 还需要验证 loops 为正数、保存逐次测量及配置，避免静默忽略 governor 设置失败。`eval_map.py --rknn-sim` 会从 ONNX 重新构建模型，不能自动代表仓库内现有 `.rknn` 的精度。

README 将 YOLOv8 替换描述为只改类别数和 anchors。当前 decoder 明确属于 YOLOv5 anchor-based 输出；切换 YOLOv8 必须核对其实际导出头、分数和解码方式，不能直接套用。

## 5. 下一轮实验顺序

### 第一轮：建立可信基线

先修复启动、评测集遗漏、帧与结果对应及失败传播；保持模型和默认阈值不变，避免把正确性修复与模型变更混在一次实验里。

建议回归验证：Python 语法检查；无帧与输入失败能按时退出；缺失检测不能缩小评测集；检测异常不继续展示正常状态；结果和 frame ID 一致；全部模型失败返回非零状态。

### 第二轮：比较现有五种模型

用同一开发板、原始模型和五个新模型、相同输入及阈值进行比较。每个模型预热至少 5 次、测量至少 50 次；这些是初步实验建议，不是已运行的结果。固定测试顺序或交替顺序，记录 CPU/NPU governor、实际频率、温度与降频情况。当前 benchmark 会设置 NPU governor，应先记录原状态并在实验后恢复。

精度评测使用固定、独立的 COCO 测试集，不与量化校准集混用。分别报告每类 AP50、precision、recall、F1 与 mAP50；项目“准确率 ≥85%”仍需明确采用哪项指标，不应直接等同于 mAP50。

根据准确率和延迟的共同表现选择模型，不仅选择最快尺寸；尤其观察远距离小头部、遮挡和多人密集场景。

### 第三轮：真实视频 QoS

默认把 QoS 理解为结果新鲜度、响应延迟、吞吐稳定性和故障恢复，而不是只增加显示 FPS。采集和推理必须使用同一单调时钟及 frame ID。至少记录：

- 采集 FPS、实际检测 FPS、显示 FPS，分别计数。
- 预处理、NPU、后处理及应用采集到结果输出的 p50/p95/p99 延迟；应用时间戳不等于传感器曝光时刻。
- 主动跳帧、积压丢帧、源读取失败，分别统计。
- 结果年龄、过期率、温度、CPU/RSS，以及检测中断和恢复次数。
- 固定场景下未戴帽 recall、误报警和报警延迟；跳帧方案必须同时评价这些指标。

运行 10–30 分钟观察稳定性；报告前必须保留原始样本、日志与配置。若 Python 后处理仍占主要耗时，再与官方 C/C++、RGA/GStreamer 路线比较；若 NPU 仍占主要耗时，优先分析算子和现有多尺寸模型，再考虑重训练更小模型。
