# 原生 App 性能优化设计

## 目标

在不修改模型、类别顺序、置信度、NMS、跳过策略、推理流水线和 1 秒 TTL 的前提下，提高板端检测与预览呈现帧率，消除换帧空档，并降低常驻进程的无意义 CPU 与存储写入。

## 已确认根因

同一板、同一 20 秒回放、同一 `helmet_416x416.rknn`：

| 场景 | 检测速率 | Qt 呈现 | Qt CPU | 管理进程 CPU |
| --- | ---: | ---: | ---: | ---: |
| UI 隐藏 | 11.10 FPS | 0 | 2.65% | 5.45% |
| UI 显示，现有 base64 JSON | 7.45 FPS | 4.30 FPS | 56.50% | 6.95% |
| 双 Image 直接读取二进制帧探针 | 9.41 FPS | 约 7.3 FPS | 36.13% | 未控制 |

隐藏 UI 时检测仍只有 11.10 FPS；空闲管理器实测约每 8.2 秒重写一次 `record.json` 的 1 秒平均值为 8.2 次/秒，并同步 `fsync`。服务生命周期记录也约每 0.25 秒写一次。两层私有状态写入与预览编码、Qt 解码共同争用 CPU。

## 方案

采用精确帧令牌和二进制直传：

1. 服务发布检测结果时为 JPEG 使用质量 80，并保留最近 4 个不可变预览包。
2. 每个预览包具有短随机 `frame_token`，同时保留 `frame_id`、`captured_at`、`generation`、`source_epoch` 和剩余 TTL。
3. 本机 QML 以小体积 `/api/preview-meta` 请求取得已编码帧的完整元数据，再用 `frame_token` 让双 Image 中的一个直接从 `/api/frame` 加载 JPEG。该缓冲只有在 `Image.Ready` 且全部既有校验通过后才显示。
4. `/frame.jpg?frame_token=` 对精确令牌返回同一 JPEG；缓存被淘汰、源中断或 TTL 到期时返回失败，不能回退为“最新帧”。
5. LAN 页面继续使用现有只读状态入口，但状态仅携带元数据和令牌，手机浏览器用精确二进制 URL 加载图片，不再传输 base64。
6. `/api/preview` 的 base64 响应保留兼容性，供既有工具和测试使用；原生 App 不再走这条热路径。
7. 管理器只在应用/进程/进度状态变化或 5 秒心跳时原子写 owner record；服务生命周期收据改为 1 秒间隔。停止和失败路径仍立即发布真实终态。

## 不变量

- `person` 仍是裸头，`hat` 仍是戴帽头部。
- conf `0.35`、NMS `0.45`、skip `0`、TTL `1.0s` 不变。
- 不修改 Pipeline、`yolo_post.py`、报警阈值、模型或输入源枚举。
- 双 Image 不得先隐藏旧图再加载新图。
- `generation`、`source_epoch`、`frameExpires`、`minimumCaptureAt`、`detection.valid` 和 `detection.running` 校验全部保留。
- 断流后只可显示到原采集时刻的 1 秒 TTL，禁止把旧图或超龄令牌当作新帧。
- 任何“请求受理”都不能替代真实退出、锁释放和进程消失证据。

## 否决方案

- 只降 JPEG 质量：可以缩小载荷，但仍保留大型 base64 JSON 和重复序列化。
- 修改模型尺寸、降低 conf 或跳帧：违背现有算法和安全契约，不能作为显示优化。
- 把预览改写成 C++/QML 插件：理论上可继续降低开销，但需要新增原生构建链，超出本轮最小闭环。
- 直接删除 TTL 或 generation 校验换取流畅：会产生旧画面误导，禁止采用。

## 验收

1. 单元与回归测试通过，并新增精确令牌、缓存淘汰、TTL/epoch、无 base64 热路径和记录写入合并测试。
2. 同一回放重复运行可量化比较检测 FPS、Qt 呈现 FPS、Qt CPU、JSON/JPEG 体积。
3. 物理摄像头接入后记录检测 FPS、呈现 FPS、端到端延迟和 180 秒稳定性。
4. 实际板屏连续观测无空白或占位文字闪烁。
5. 运行中拔摄像头，实际画面在最迟 1 秒内清空。
6. 常驻、双图标复用、正常退出与锁释放回归不退化。
